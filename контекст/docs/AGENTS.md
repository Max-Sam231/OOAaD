# AGENTS.md — инструкции для ИИ-агентов

Проект: игровой сервер «Космический бой», дисциплина ООАиП. Курс про архитектуру с атрибутом качества «модифицируемость», а не про разработку игр.
Код: `SpaceBattle/` (решение `SpaceBattle.sln`). Задачи: `docs/ROADMAP.md`. Решения: `docs/DECISIONS.md`.

## Команды

```bash
cd SpaceBattle
dotnet build
dotnet test --collect:"XPlat Code Coverage"
```

## Архитектурные правила (обязательны)

Преподаватель не принимает код, сгенерированный в обход этой архитектуры.

1. Любое действие — класс, реализующий `App.ICommand` (`void Execute()`).
2. Не создавать зависимости через `new` в прикладном коде: только `Ioc.Resolve<T>("Имя", args)`.
3. Каждая зависимость регистрируется отдельной командой `RegisterIoCDependency<Имя> : ICommand` через `Ioc.Resolve<ICommand>("IoC.Register", "Имя", (Func<object[], object>)(args => ...)).Execute()`.
4. Имена зависимостей: `Commands.*`, `Actions.*`, `Game.*`, `Specs.*`, `Adapters.*`.
5. Новое поведение добавляется новыми файлами и регистрациями. Существующие классы не переписывать ради новой фичи (OCP).
6. Композиция вместо наследования: составное поведение — `MacroCommand`, состав в `Specs.<операция>`. Циклы в макрокомандах запрещены.
7. Игровой объект — `IDictionary<string, object>`. Команды работают через интерфейсы (`IMovable`, `IRotatable`, …), доступ — через адаптеры.
8. Зависимости класса — через конструктор, с проверкой на `null` (`ArgumentNullException`).
9. У каждой игры свой scope IoC. `Game` не переключает scope сам — это делает `InSeparateScopeCommand`.
10. Не добавлять пакеты NuGet без записи обоснования в `DECISIONS.md`.

## Тесты

- xUnit + Moq. Каждый новый класс — с тестами, включая исключительные ситуации.
- Покрытие PR ≥ 90 % (проверяет CI, иначе PR не проходит).
- В тестах IoC инициализировать через `new InitCommand().Execute()`, новый scope на тест (`IoC.Scope.Create`, `IoC.Scope.Current.Set`).
- Внешние зависимости в тестах мокать, а не регистрировать настоящие реализации.

## Процесс

- Одна задача = Issue на GitHub + отдельная ветка, созданная на GitHub; слияние через PR.
- Коммиты в стиле Conventional Commits: `feat:`, `fix:`, `test:`, `refactor:`, `style:`, `chore:`.
- Перед PR: `dotnet format`, сборка и тесты зелёные.
- Принятое архитектурное решение — запись в `docs/DECISIONS.md`. Выполненная задача — отметка в `docs/ROADMAP.md`.
- Код должен быть понятен авторам: на зачёте спрашивают, как он работает.
