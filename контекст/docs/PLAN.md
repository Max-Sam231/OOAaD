# ООАиП: общий план проекта до зачёта

Цель к зачёту (конец декабря 2026): игровой сервер «Космический бой», в котором игра задаётся текстовым описанием и в неё можно играть. Правила добавляются регистрацией в IoC без правки кода, игры работают в нескольких потоках и переезжают между двумя серверами.

План собран по вики курса, ПЗ 1–4 и event storming. Если преподаватель выдаст лабы (обещал сдвоенные: «месяц нету, потом четыре лабы»), план сверяем с ними.

## Этап 1. Запускаемый сервер (27 окт – 9 ноя)

Подробно расписан в `TASKS.md`.

- [ ] Влить `feature/5lab` (кодогенерация адаптеров) и ветки с коллизиями
- [ ] `InSeparateScopeCommand` + зависимость `Game.Create`, scope убрать из `Game.Execute`
- [ ] Консольный `SpaceBattle.Server`, игра выполняется квантами по N тиков
- [ ] WebSocket endpoint: JSON → команда через IoC → очередь игры; рассылка состояния с номером шага
- [ ] Демо: правило «топливо» новыми файлами, старый код не меняется

## Этап 2. Игра из текстового описания (10 – 16 ноя)

- [ ] Формат описания (JSON или YAML): объекты, их свойства, правила, состав макрокоманд `Specs.*`
- [ ] Загрузчик: описание превращается только в последовательность `IoC.Register` в scope игры
- [ ] Общая стратегия макрокоманды: имя операции передаётся параметром (`<операция>.config`)
- [ ] Две игры из двух описаний ведут себя по-разному при одном и том же коде

## Этап 3. Правила из event storming (17 – 30 ноя)

- [ ] Движение в точку: контроль достижения точки, остановка двигателей
- [ ] Топливо: расход, «движение невозможно» при пустом баке
- [ ] Дозаправка: запрос, проверка расстояния и наличия топлива, пополнение
- [ ] Выстрел: проверка ракет → создание торпеды по правилам → движение; отказ, если ракет нет
- [ ] Коллизия: определить, с чем столкнулись → уничтожить объект или применить бонус
- [ ] Метеориты: объекты, летящие по прямой с постоянной скоростью
- [ ] Условия завершения игры → матч завершён

## Этап 4. Многопоточность (1 – 14 дек)

- [ ] ServerThread: потокобезопасная очередь + планировщик квантов между играми
- [ ] Поток не спит на пустой очереди, если есть игра, готовая выполняться
- [ ] Реалтайм-схема: рассылка состояния → N тиков → игра ждёт решения всех агентов
- [ ] Перенос игры между потоками без взаимной блокировки (отдельная очередь или неблокирующая запись с повтором)
- [ ] Тесты на перемешанный порядок сообщений и на блокировки
- [ ] Нагрузочный тест endpoint: десятки тысяч сообщений в секунду локально

## Этап 5. Сериализация и scope'ы (15 – 21 дек)

- [ ] Команды в JSON: `id`, `type`, `game_item_id`; Macro — список id; Repeater — id повторяемой команды
- [ ] Сериализация очереди и game items; несериализуемое (ссылки, scope) восстанавливается при загрузке
- [ ] Досбор сообщений, пришедших во время переноса
- [ ] Восстановление scope игры в IoC на целевом сервере
- [ ] Демо: два серверных процесса, игра переезжает и продолжает играть
- [ ] Иерархия scope'ов: корень (системное) → слой игр (Move, Rotate…) → игра; глубина ≤ 4
- [ ] Горячее обновление: копия общего scope + scope-посредник, переключение одной сменой `Parent`

## Этап 6. Окружение игры и бонусы (22 – 28 дек)

- [ ] Регистрация и вход игрока, проверка владельца при командах
- [ ] Заявка → лобби → выбор правил → создание сессии → генерация объектов
- [ ] Подведение итогов, архив боя, статистика
- [ ] Бонус: транзакции через журнал изменений и двухфазный коммит
- [ ] Репетиция показа: каждый объясняет свою часть

## Правила на весь проект

- Любое действие — `ICommand`, объекты создаются через `Ioc.Resolve`, без `new` в прикладном коде.
- Новое поведение — новые файлы и регистрации, старые классы не переписываем.
- Составное поведение — макрокоманды, не наследование.
- Каждая задача — Issue + ветка + PR, покрытие ≥ 90 %.
- Коммитить часто: по истории должно быть видно, что работа шла все два месяца.
- Код от ИИ допускается, но только по этой архитектуре, и каждый должен понимать свой код.
