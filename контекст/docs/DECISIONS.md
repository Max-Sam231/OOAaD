# DECISIONS — журнал архитектурных решений

Формат записи: дата, решение, контекст, альтернативы, последствия.
Статус: **принято** — уже в коде; **предложено** — нужно обсудить в команде и подтвердить.
Новые решения добавляйте в конец, старые не удаляйте (при отмене пишите новую запись).

## D-001. Стек: C# / .NET 10, xUnit, Moq — принято

- Контекст: требование курса (ЛР2), IoC поставляется как `Common/core.dll`, `Common/scopes.dll`.
- Последствия: CI на GitHub Actions, покрытие PR ≥ 90 %, сборка один раз на прогон.

## D-002. Всё поведение — команды `ICommand`, создание объектов — через IoC — принято

- Контекст: ПЗ1 — строка `new Move(obj)` фиксирует тип, количество и время создания.
- Решение: `Ioc.Resolve<ICommand>("Commands.X", ...)`, регистрация в классах `RegisterIoCDependencyX`.
- Последствия: новое поведение = новая регистрация, существующий код не меняется.

## D-003. Расширение поведения — композиция объектов (макрокоманды), не наследование — принято

- Контекст: ПЗ1 — наследование фиксируется при компиляции, а правила игр различаются в рантайме.
- Решение: `MacroCommand`, состав берётся из `Specs.<операция>`; исходная команда всегда внутри макрокоманды.

## D-004. Игровой объект — `IDictionary<string, object>`, доступ через адаптеры — принято (ЛР5 в ветке)

- Решение: адаптер к интерфейсу генерируется по рефлексии; get → `Ioc.Resolve<T>("<Интерфейс>:<Свойство>.Get", obj)`, set → `...Set`.
- Нестандартные свойства (например Velocity) задаются атрибутом `[Adapter(typeof(I), "Prop", ...)]` на уровне сборки.
- Последствия: разработчику новой команды нужно написать только команду, интерфейс и нестандартные стратегии.

## D-005. Коллизии — предрасчитанная матрица (бинарная классификация) — принято

- Решение: по `(dx, dy, ddx, ddy)` ответ из заранее посчитанного набора, проверка O(1).
- Данные: `Tools/generate_matrix.py` → `Tools/collision_matrix.csv`.
- Открыто: загрузка файла в память при старте и регистрация `Game.Collision.Check`.

## D-006. Протокол endpoint — WebSocket — предложено

- Контекст: ПЗ3 — сервер сам рассылает состояние агентам, обычный HTTP «запрос-ответ» не подходит.
- Альтернативы: TCP (больше ручной работы), UDP (самый сложный), polling (допустим, но кода больше).
- Последствия: нужно хранить соединения и знать, кому что отправлять.

## D-007. Формат входящего сообщения — предложено

```json
{ "gameId": "...", "objectId": "...", "cmd": "Commands.StartMove", "step": 42, "args": { ... } }
```

- `cmd` — имя зависимости IoC; сообщение превращается в команду интерпретатором и через `Commands.Send` попадает в очередь игры.
- `step` — номер шага, на основе которого агент принял решение; сообщения со старым шагом отбрасываются (ПЗ3: агент не под нашим контролем).

## D-008. Scope на игру через `InSeparateScopeCommand` — предложено

- Контекст: ПЗ4 — одна строка `Ioc.Resolve("Movement", obj)` должна давать разное поведение в разных играх.
- Решение: `Game.Create` создаёт scope игры и оборачивает `Game` в `InSeparateScopeCommand`; `Game` о scope не знает.
- Последствия: переключение scope убрать из `Game.Execute`.

## D-009. Иерархия scope'ов — предложено

- Корень (потокобезопасный): версия ПО, каталог плагинов, аптайм.
- Слой игр: общие команды (Move, Rotate, …).
- Scope конкретной игры (обычный `Dictionary`): правила игры, переопределения.
- Глубина обхода ≤ 4 (с учётом scope-посредника для горячего обновления).

## D-010. Порядок развития: монолит → многопоточность → несколько серверов — принято (по ПЗ3)

- Сначала одна игра в простом цикле, но команды и receiver/sender пишутся так, чтобы позже обернуться планировщиком без переписывания.
