# Как работает IoC в SpaceBattle

Источники: статьи вики курса ([IoC](https://wiki.pmifi.ru/disciplines/ooaad/ioc), [IoC и области видимости](https://wiki.pmifi.ru/disciplines/ooaad/ioc-and-scopes), [IoC и тесты](https://wiki.pmifi.ru/disciplines/ooaad/IoC-And-Tests)), практические занятия 1, 2 и 4, код в `SpaceBattle/`.
Поведение `core.dll` и `scopes.dll` из раздела «Проверенное поведение» получено запуском, а не взято из описания.

## 1. Зачем он нужен

Строка `new MoveCommand(obj)` фиксирует три вещи, и любая из них может поменяться:

1. **Тип.** Если в игре появится топливо, вместо `MoveCommand` понадобится другая команда, и строку придётся переписать.
2. **Способ создания.** `new` всегда создаёт новый объект, хотя иногда выгоднее отдать уже готовый.
3. **Аргументы.** Сегодня параметр один, завтра их два или другого типа.

`Ioc.Resolve<ICommand>("Commands.Move", obj)` скрывает всё это за именем. Когда правила меняются, мы регистрируем под тем же именем другую стратегию, а строка с `Resolve` остаётся прежней. Цель курса — писать так, чтобы новое поведение добавлялось новыми файлами и регистрациями, без правки существующих строк.

## 2. Из чего состоит

Контейнер лежит в двух закрытых библиотеках в `SpaceBattle/Common/`:

| Библиотека | Пространство имён | Что даёт |
| --- | --- | --- |
| `core.dll` | `App` | `ICommand { void Execute(); }` и `Ioc.Resolve<T>(string dependency, params object[] args)` |
| `scopes.dll` | `App.Scopes` | `InitCommand` и зависимости `IoC.*` для регистрации и скоупов |

У контейнера один метод — `Resolve`. Регистрация, создание скоупа, смена скоупа — это тоже зависимости, которые разрешаются через него же.

Зависимость состоит из имени и **стратегии** типа `Func<object[], object>`: функция получает аргументы `Resolve` и возвращает объект. `Resolve<T>` находит стратегию по имени, вызывает её и приводит результат к `T`.

## 3. Регистрация и разрешение

`IoC.Register` возвращает команду. Зависимость появляется только после `Execute()`:

```csharp
Ioc.Resolve<ICommand>(
    "IoC.Register",
    "Commands.Move",
    (object[] args) =>
    {
        var moving = Ioc.Resolve<IMovingObject>("Adapters.IMovingObject", args);
        return new MoveCommand(moving);
    }
).Execute();
```

Использование:

```csharp
var move = Ioc.Resolve<ICommand>("Commands.Move", ship);
move.Execute();
```

Регистрация записывается в **текущий** скоуп.

Стратегия сама решает, создавать ли новый объект. Команду без состояния можно создать один раз и возвращать каждый раз её же (пример из вики с `EmptyCommand`). У нас так сделан репозиторий: `RegisterIoCDependencyGameObjectRepository` создаёт один `GameObjectRepository` и отдаёт его по двум именам — `Game.Repository.ReadOnly` и `Game.Repository.Writable`.

## 4. Как это устроено в нашем коде

**Одна зависимость — одна команда регистрации.** Каждый класс `RegisterIoCDependency<Имя> : ICommand` в `SpaceBattle.Lib/Commands/` регистрирует свои зависимости в `Execute()`. `new` допустим только внутри стратегии.

**Имена зависимостей** строятся так, чтобы их можно было угадать без документации:

| Префикс | Что лежит | Примеры |
| --- | --- | --- |
| `Commands.*` | создание команды | `Commands.Move`, `Commands.Rotate`, `Commands.Shoot`, `Commands.Macro`, `Commands.Send` |
| `Adapters.*` | адаптер игрового объекта к интерфейсу | `Adapters.IMovingObject` |
| `Specs.*` | список имён команд для макрокоманды | `Specs.Move` |
| `Macro.*` | макрокоманда, собранная по `Specs.*` | `Macro.Move`, `Macro.Rotate` |
| `Actions.*` | длительные операции | `Actions.Start`, `Actions.Stop` |
| `Game.*` | сервисы игры | `Game.Repository.ReadOnly`, `Game.Loop.CanContinue` |

Полный список с аргументами — в [`.memory-bank/context.md`](../.memory-bank/context.md).

**Макрокоманда через IoC.** `CreateMacroCommandStrategy` берёт список имён из `Specs.<операция>`, разрешает каждое имя в команду и оборачивает результат в `Commands.Macro`. Чтобы добавить в движение сжигание топлива, достаточно зарегистрировать другой список в `Specs.Move`; ни `MoveCommand`, ни стратегия не меняются.

**Адаптеры.** Игровой объект — это `IDictionary<string, object>`. Команды работают с ним через интерфейсы (`IMovingObject`, `IRotatingObject`), а объект, реализующий интерфейс поверх словаря, приходит из `Adapters.*`. Сейчас в `SpaceBattle.Lib` эти зависимости только запрашиваются; регистрировать их будет кодогенерация адаптеров.

**Внедрение через конструктор.** Команда получает зависимости параметрами конструктора, а `Resolve` вызывается в стратегии регистрации. Так сделан `SendCommand(command, receiver)`. Такую команду можно тестировать вообще без IoC — это рекомендация из вики.

## 5. Скоупы

### Задача

На сервере идёт несколько игр с разными правилами. Строка `Ioc.Resolve<ICommand>("Macro.Move", ship)` должна оставаться одной и той же, а результат — зависеть от игры: в одной движение тратит топливо, в другой нет.

Для этого у каждой игры свой **скоуп** — словарь «имя → стратегия». `Resolve` ищет имя в текущем скоупе.

### Зависимости для работы со скоупами

| Имя | Аргументы | Результат |
| --- | --- | --- |
| `IoC.Scope.Create` | родитель (необязательно) | новый скоуп; без аргумента родителем станет текущий |
| `IoC.Scope.Create.Empty` | — | скоуп без родителя |
| `IoC.Scope.Current` | — | текущий скоуп потока |
| `IoC.Scope.Current.Set` | скоуп | команда, делающая скоуп текущим |
| `IoC.Scope.Current.Clear` | — | команда, возвращающая поток к корневому скоупу |
| `IoC.Scope.Parent` | — | родитель текущего скоупа |

В вики те же зависимости названы `Scopes.Create` и `Scopes.Current.Set`. В нашей `scopes.dll` имена начинаются с `IoC.Scope.`.

```csharp
new InitCommand().Execute();

var gameScope = Ioc.Resolve<object>("IoC.Scope.Create");
Ioc.Resolve<ICommand>("IoC.Scope.Current.Set", gameScope).Execute();
```

`IoC.Scope.Create` не меняет текущий скоуп — его нужно установить отдельно.

### Иерархия

У каждого скоупа, кроме корневого, есть родитель. Если имени нет в текущем скоупе, `Resolve` ищет его у родителя и так далее до корня. Отсюда два следствия:

- **Общее не дублируется.** `Commands.Move` и `Commands.Rotate` регистрируются один раз в общем скоупе, и все игры видят их через родителя.
- **Частное переопределяется.** Игра регистрирует в своём скоупе `Specs.Move` с топливом, и это не влияет ни на родителя, ни на соседние игры.

Каждый уровень иерархии — дополнительный поиск перед тем же самым `new`, поэтому глубину обхода нужно держать небольшой. Инвариант проекта `INV-7`: не больше 4.

### Потоки

Текущий скоуп хранится отдельно для каждого потока (`ThreadLocal`). В одном потоке в каждый момент выполняется не больше одной игры, поэтому достаточно установить её скоуп перед выполнением.

Корневой скоуп потокобезопасный, остальные — нет. Скоуп игры можно читать и менять только из того потока, где игра сейчас выполняется. Общий родительский скоуп игры из разных потоков могут читать одновременно, но писать в него во время игр нельзя.

### `InSeparateScopeCommand`

`Game` ничего не знает о скоупах (`INV-7`). Скоуп переключает обёртка `SpaceBattle.Lib/Game/InSeparateScopeCommand.cs`:

```csharp
public void Execute()
{
    var previousScope = Ioc.Resolve<object>("IoC.Scope.Current");
    var restoreScope = Ioc.Resolve<ICommand>("IoC.Scope.Current.Set", previousScope);
    Ioc.Resolve<ICommand>("IoC.Scope.Current.Set", _targetScope).Execute();

    try
    {
        _innerCommand.Execute();
    }
    finally
    {
        restoreScope.Execute();
    }
}
```

Она запоминает прежний скоуп, ставит нужный, выполняет внутреннюю команду и в `finally` возвращает прежний. Код до и после вызова не замечает, что скоуп менялся. Игра кладётся внутрь такой команды, и поток работает только с обёртками.

Команда восстановления создаётся **до** смены скоупа. Иначе `IoC.Scope.Current.Set` пришлось бы разрешать уже в целевом скоупе, а он может оказаться пустым (см. ниже).

## 6. IoC в тестах

Каждый тестовый класс начинает с чистого скоупа:

```csharp
public MoveCommandTests()
{
    new InitCommand().Execute();
    var scope = Ioc.Resolve<object>("IoC.Scope.Create");
    Ioc.Resolve<ICommand>("IoC.Scope.Current.Set", scope).Execute();
}
```

Зависимости, которые нужны проверяемому классу, регистрируются в этом скоупе как подстановки (`Substitute.For<...>()` из NSubstitute), а не настоящими реализациями. В примерах вики используется Moq — приём тот же.

Новый скоуп на тест нужен обязательно: повторная регистрация того же имени в том же скоупе падает (см. ниже).

## 7. Проверенное поведение и ловушки

| Ситуация | Что происходит |
| --- | --- |
| `Resolve` до `new InitCommand().Execute()` | `ArgumentException: Dependency {dependency} is not found.` |
| Имя не найдено ни в одном скоупе до корня | `Exception: The root scope has no a parent scope.` — в сообщении нет имени зависимости |
| Повторный `IoC.Register` того же имени в том же скоупе | `ArgumentException: An item with the same key has already been added` |
| То же имя в дочернем скоупе | работает; дочерний скоуп перекрывает родителя, родитель не меняется |
| Новый поток, скоуп не установлен | текущий скоуп — корневой |
| Текущим сделан скоуп из `IoC.Scope.Create.Empty` | не разрешается ничего, включая `IoC.Register` и `IoC.Scope.Current.Clear`: `KeyNotFoundException: 'IoC.Scope.Parent'` |

Корневой скоуп — `ConcurrentDictionary<string, Func<object[], object>>`, остальные — обычный `Dictionary` того же типа. Ссылка на родителя лежит в самом скоупе под именем `IoC.Scope.Parent`.

Выводы для проекта:

- Переопределить зависимость в том же скоупе нельзя. Новое правило для игры регистрируется в её собственном скоупе, а обновление общих команд требует нового скоупа.
- Ошибку «The root scope has no a parent scope» нужно читать как «зависимость не зарегистрирована в текущей ветке скоупов». После переноса игры на другой сервер она появится, если скоуп игры не восстановлен.

## 8. Что запланировано

Этого в коде ещё нет; схема — из ПЗ4 и документов в `контекст/docs/`.

- **Слои скоупов:** корень (системное: версия, каталог плагинов) → слой игр (`Commands.Move`, `Commands.Rotate`) → скоуп конкретной игры (её правила и переопределения).
- **Создание игры:** зависимость, которая создаёт скоуп игры, саму `Game` и возвращает её внутри `InSeparateScopeCommand`.
- **Горячее обновление:** между слоем игр и играми стоит скоуп-посредник. Обновления накапливаются в копии общего скоупа, затем у посредника одной записью меняется `Parent`, и все игры одновременно видят новую версию.
